## Changes

- Enrolment step 2 box-key deadlock fix (follow-up to the enrolment deadlock fix, PR 311): the box key write began with a revoke `UPDATE` that matches no row on a sprout's first key and left a gap lock on `idx_pki_sprout_box_keys_one_active`, which every other sprout's INSERT then waited on, so sprouts enrolling in the same second deadlocked (1213) on each other, across tenants too. They were retried, so nothing failed, but the 60-sprout MySQL test counted 39 to 143 deadlocks a run. `upsertSproutBoxKeyActive` now inserts first and takes the revoke-and-upsert path only on a duplicate key (a replay of the same key, or another key active). The fast path is a plain INSERT, not an upsert, since ON DUPLICATE KEY UPDATE on the one-active index would update the other key's row. The same test now counts 0 deadlocks a run, at 60 and at 200 sprouts. A new MySQL test holds one tenant's first box-key and pki_nkeys writes open and checks that another tenant's do not wait on them; on the old code both waited out the lock timeout (1205).
- Enrolment deadlock fix (launch risk for mass enrolment; in rc.16 to rc.18): sprouts enrolling in the same second deadlocked (MySQL 1213) on `pki_nkeys`, because each enrolment's `SELECT ... FOR UPDATE` took next-key locks over its tenant's range and the gap after it, which every other first enrolment's INSERT then waited on, across tenants too. The join token's use had already been committed by a separate UPDATE, so the loser's single-use token was burned and its retries were refused as exhausted (401). Farmer now redeems the use and accepts the sprout in one transaction, retried on 1213, 1205 and SQLite busy with jittered back-off (6 tries), inserts the `pki_nkeys` row first and takes the locking path only on a conflict, re-resolves the sprout ID if another host took it mid-enrolment, and answers a transient database failure 503 with Retry-After (3 s), keeping 401 for a refused credential. The sprout logs a 401 once at error level, naming the key_id and what to do, then retries only every 5 minutes with a one-line warning; a 503 is a warning. New MySQL test: 60 sprouts in 5 tenants, with the same sprout IDs in each tenant, enrolling at once. Before the fix 49 to 55 of the 60 failed; after it all 60 enrol in every run (also checked at 200 sprouts). The lite rig could not run in this session (kind's nested containers do not start there), so the rig check waits for the next rc. Still open: a failure after the commit (Account grant, User JWT mint) strands the sprout, because the replay path refuses an accepted sprout with no box key.
- I.pkg.repo_managed on Ubuntu (rc.19 lite rig, real cook failed with an empty `add-apt-repository: exit status 1: `): Ubuntu 24.04's add-apt-repository refuses a one-line flat repository ("Unable to handle repository shortcut 'deb [trusted=yes] file:... ./'") and prints that on stdout, which snack's AddRepo never reads. On apt, `pkg.repo_managed` now writes /etc/apt/sources.list.d/<name>.list (one-line entries, [options] such as trusted=yes, signed-by, arch) or <name>.sources (deb822) itself and runs apt-get update, reverting the file if the update fails; `absent` deletes the file. Idempotency comes from that file's content, so a second cook reports no change and a changed url rewrites it. dnf/yum/zypper keep snack's path. Errors from shelled-out commands in the pkg, cron, group, user, selfupdate and winexec ingredients now quote both stderr and stdout (`ingredients.CommandError`). Reproduced and checked in an Ubuntu 24.04 container, not on the rig (this session could not run it).
- pkg.repo_managed on apt takes `ppa:<owner>/<name>` (or `ppa:<owner>`) again: #313 wrote apt sources itself and rejected add-apt-repository shortcuts; a PPA now goes through snack's AddRepo/RemoveRepo (add-apt-repository, which also fetches the PPA's key and updates the lists), with `absent` removing it by the same shortcut. Whether it is configured is read from the source files (the PPA's Launchpad URI on either host, in sources.list, `.list` or deb822 `.sources`), not snack's ListRepos, which never matches a PPA by name and doesn't read the `.sources` file 24.04 writes, so a second cook reports no change. A missing add-apt-repository is named (software-properties-common), and a run that leaves no source behind fails. Other shortcuts (cloud-archive:, uca:) are still refused. Unit-tested; the live check in an Ubuntu 24.04 container could not reach Launchpad from this session, so a real PPA add is unverified.
- UAT harness, Keycloak lockout flake (rc.19 lite rig: `token for t1-admin ... HTTP 401 invalid_grant Invalid user credentials`, Keycloak logging user_temporarily_disabled with no failed login before it). Keycloak 26.4 sets that lockout only when it counts failed logins, and with failureFactor 30 only its quick-login rule could fire this early: two counted failures less than 1 s apart lock the user for 60 s, and Keycloak answers a locked-out user exactly as it answers a wrong password. The cause of the failures is not confirmed. `harness.Tokens` now sends one password grant per user at a time, however many parallel cases miss the cache, and waits out a refusal (up to 150 s, logged as `uat harness: Keycloak refused ...`) when that password already got a token in the run; a password that never worked still fails at once. The UAT Keycloak logs its brute-force protector at debug, and diagnostics.sh writes `<hub>/keycloak/<ns>.<pod>.txt` (the whole log's login-error and brute-force lines, then the last lines) for every Keycloak pod, healthy or not, so the next lockout leaves its login errors and the failure counts and timing that set it.
