change: Enrolment deadlock fix (launch risk for mass enrolment; in rc.16 to rc.18): sprouts enrolling in the same second deadlocked (MySQL 1213) on `pki_nkeys`, because each enrolment's `SELECT ... FOR UPDATE` took next-key locks over its tenant's range and the gap after it, which every other first enrolment's INSERT then waited on, across tenants too. The join token's use had already been committed by a separate UPDATE, so the loser's single-use token was burned and its retries were refused as exhausted (401). Farmer now redeems the use and accepts the sprout in one transaction, retried on 1213, 1205 and SQLite busy with jittered back-off (6 tries), inserts the `pki_nkeys` row first and takes the locking path only on a conflict, re-resolves the sprout ID if another host took it mid-enrolment, and answers a transient database failure 503 with Retry-After (3 s), keeping 401 for a refused credential. The sprout logs a 401 once at error level, naming the key_id and what to do, then retries only every 5 minutes with a one-line warning; a 503 is a warning.
