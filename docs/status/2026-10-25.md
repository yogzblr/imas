## Changes

- P35: a panic in an ingredient step (a nil map, a bad type assertion, a COM wrapper bug) no longer crashes the sprout. The cook path recovers it around every step's Test and Apply, on_exit steps included, and fails that step with an error naming the step, ingredient, method and mode, the panic value and the panicking goroutine's stack (8 frames); the job completes and later steps run. A Windows step bounded by IMAS_WINDOWS_STEP_TIMEOUT runs in a goroutine of its own, so it recovers there too, and a step abandoned at the bound that panics later still releases its fence, so later steps of the same ingredient are not blocked (review on #320). Proven by unit tests with fake panicking cookers, run with -race. (PR #321)
- W11 (Part D): a CI workflow, .github/workflows/ingredients-os.yml, runs the UAT case catalogue's cycle (setup, test mode, real cook, idempotency, out of band check, revert) for the Windows ingredients on a GitHub Windows Server 2022 runner (win_firewall, win_task, win_dacl, win_certutil, win_psget, win_shortcut and its child process, user, group, service, registry, win_dsc) and for the service cases against real systemd on an Ubuntu runner and in an AlmaLinux 9 container with systemd as PID 1 (plus a static unit), with no hub, bus or Azure: a local driver cooks each step through the registered ingredients and runs the case scripts on the machine. It runs on pull requests touching those ingredients, the cases or the harness. It does not cover Server Core, the sprout's SYSTEM context, the sprout process or the Bastion channel, which stay with the Azure UAT run.
