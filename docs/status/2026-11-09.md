## Changes

- W15: farmer and saasapi bound every wait on a database peer that died without closing its connections. Run 3 on v0.1.0-rc.23 (run 42542177384, HA2 core) failed its 60 s window: cmd.run was not served for 2m17s after uat-core-1 stopped, while PXC failed over in about 33 s (HAProxy marked pxc-0 down and cut its sessions). The pods on the stopped node (haproxy-1, pxc-0) died with no FIN or reset, and both DSNs set no timeout, readTimeout or writeTimeout and the pools no idle limit, so a new connection to the dead HAProxy pod waited on SYN retries and a pooled one hung on the dead socket. `internal/mysqldsn` now adds timeout=5s, readTimeout=60s (above InnoDB's 50 s lock wait, so a slow lock wait still ends in error 1205, which pki retries) and writeTimeout=30s to any DSN that does not set them, and sets ConnMaxIdleTime 30s and ConnMaxLifetime 5m; `pxc.OpenDB` and `saasapi.OpenDB` apply both. A new test opens farmer's DB against an address that never answers: 5 s with the change, 2m14s without (HA2's outage was 2m17s). Proven by unit tests; the HA run is the end-to-end check. (PR #330)
- W16: HA5 (lost event) compares the repaired bus loader with the other loaders' index as it is when checked, not as it was before the block lifted. Run 3 on v0.1.0-rc.23 (run 42542177384) failed HA5 with the loader repaired: 6 of 6 accounts, 2 pushes, and the following step passed (every bus node refused the revoked sprout and accepted the new tenant's); only its index token differed from the stored one. Every index write is a fresh random token, and a loader that applies a change by its event moves its token only at its next timer pass (30 s ±20%). HA5's two writes (the new account at 02:41:15, the revocation at 02:41:36) came 21 s apart, so the other loaders could agree on the first while the repaired loader went straight to the second. No product code changed; checked by vet and a compile of the uat tests (they run only against a UAT environment). (PR #331)
