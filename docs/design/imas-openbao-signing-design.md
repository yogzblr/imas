## 1. Why

Farmer cannot scale horizontally today (`farmer.replicaCount` is forced to 1) because signing keys and JWTs live on one ReadWriteOnce PVC:

- six platform NKey seeds are generated by ops outside the platform and delivered as a Kubernetes Secret (ESO from OpenBao). Farmer and the bus must hold byte-identical copies;
- per-tenant Account and signing seeds (`account.nk`, `account-signing.nk`) are generated by farmer at provisioning and written to the PVC;
- per-sprout User JWTs are files on the PVC.

Goal: no person and no pod ever holds a private signing key; farmer and the bus hold no sprout or tenant state; farmer and the bus scale out.

## 3. Terms

- Auto-unseal: the root key is wrapped by an external seal key (HSM/KMS). `operator init` then yields recovery keys, not unseal keys. Pods unseal themselves on start.
- Static seal (test): the seal key is a file supplied from a Kubernetes Secret. Same code path as production, no external dependency. Not acceptable for production because anyone who can read the Secret and the Raft data can unseal (CONFIRM static seal is available in the pinned version).
- Transit key: Ed25519, `exportable=false`, `allow_plaintext_backup=false`. Farmer calls `sign`; the private key never leaves OpenBao.

|---|---|---|

| Azure | `azurekeyvault` | External plugin |

Which plugins go into the image, and how they are pinned (binary or OCI digest), is a build decision to settle from OpenBao's plugin docs.

### 3.2 KMIP seal requirements (openbao.org/docs/configuration/seal/kmip/)

- Config: `endpoint`, `kms_key_id`, `client_cert`, `client_key` (required); `ca_cert`, `server_name`, `timeout` (default 10 s), `encrypt_alg`, `tls12_ciphers` (optional).
- KMIP 1.2, 1.3 or 1.4. The server must support **Encrypt and Decrypt** (not just key management). Key types: AES (`AES_GCM`, default) or RSA (`RSA_OAEP_SHA256/384/512`).
- OpenBao does **not** create the key. It must already exist on the KMIP server and be **active**.
- Rotation: create a new key on the server, change `kms_key_id`, restart. **Old keys must be kept**; they decrypt existing data. This ties into recovery (section 10): a snapshot restore needs the seal key that wrapped it, so retired keys stay until no snapshot depends on them.
- Tested servers: PyKMIP (AES_GCM only; needs the TLS 1.2 cipher `TLS_RSA_WITH_AES_128_CBC_SHA256` allowed) and OVHcloud KMS.
- The KMIP client certificate and key are needed **before** OpenBao is unsealed, so they cannot be issued by OpenBao's own PKI. They come from the KMIP operator or a separate CA and are mounted from a Kubernetes Secret. Their expiry and rotation is an operational duty (an expired client cert plus a restart means OpenBao cannot unseal).

### 4.1 Fleet update trust (BUILD-STATUS P18, P20, P22)

**Decision D9.** Update integrity comes from the release's GPG-signed `checksums.txt`. Today `.goreleaser.yaml` already builds `checksums.txt` (all packages plus the MSI) and signs it with `gpg2 --detach-sign` (`checksums.txt.sig`; a keyless cosign bundle is also produced). The Transit key `imas-fleet-signing`, the `fleetreleaser` service and the Ed25519 manifest signature are no longer needed for this path.

Why the sprout needs a signature at all: it installs with `dpkg -i` / `rpm -U` on a downloaded file, which checks no repository signature. The SHA-256 is the only integrity check, so the thing that carries the hash must be signed by a key farmer does not control. A GPG `.sig` sent by farmer is useless unless the verifying public key is already on the sprout, so the key ships in the package.

Flow:

1. Release: GoReleaser publishes `checksums.txt` and `checksums.txt.sig`, signed with the release GPG key (CI secret `GPG_PRIVATE_KEY`; the signature is checked in the release workflow before publish).
2. Registration (operator plane): saasapi stores, per version, the verbatim `checksums.txt` and `checksums.txt.sig` bytes. It no longer calls `fleetreleaser`. It validates the signature against the public key before storing, as a sanity check only; the sprout is the verifier.
3. Update: the sprout asks farmer for the manifest for its approved version (as today). Farmer returns the signed `checksums.txt` bytes, the `.sig`, and the `file_name` it should install.
4. The sprout verifies the `.sig` over the exact `checksums.txt` bytes with the GPG public keys in `fleet-signing-keys` (now a GPG keyring file), finds the line for `file_name`, downloads from the repository configured in the sprout, and requires the SHA-256 to match.
5. The sprout derives the expected `file_name` itself from its own OS, arch, package type and the version, and refuses a different name. This replaces the OS, arch and version binding the old manifest signed. `min_sprout_version` and the tenant's approved version stay farmer policy (not signed); the sprout keeps its downgrade refusal (`dpkg --refuse-downgrade`, version comparison).

What this changes and what it does not:

- It fixes P18 once the real GPG public key is in the package, and a release check parses the keyring (below). It removes the per-rig key mismatch: the key is the release key, not one made by each OpenBao.
- It removes P20 option C's need to deploy `fleetreleaser` and its signing key. The UAT still needs the operator plane, a TLS Secret and a token to register a release. It needs no special keyring: UAT installs the `rc` packages from the same release workflow, signed with the same release GPG key, so it follows the production path (owner, 2026-10-11).
- Custody moves from Transit/HSM to the GPG key in CI secrets. It must be a dedicated release key with a passphrase, available only to the `goreleaser` environment (protected tag/environment). Its compromise lets an attacker sign any update: revocation means shipping a new keyring in a package that the old key signed.
- A compromised farmer can still choose which signed release a tenant gets (an older signed version), but cannot create an unsigned one. Downgrade protection stays on the sprout.
- Rotation: the keyring holds more than one GPG key. A new key ships in a release signed by the old one; the old key is removed only when no approved version needs it. Same rule as the Ed25519 keyring.

Licence decision (owner, 2026-10-11): BSD-3-Clause is acceptable, so `github.com/ProtonMail/go-crypto` (already an indirect dependency) may become a direct dependency for GPG verification; record it in `DEPENDENCIES.md`. Open points: whether to also verify the cosign bundle (not needed for the sprout, which has no network path to Sigstore); how a customer who mirrors packages supplies their own signed checksums (they republish the same signed file).

Release check (P18): the release workflow fails if the shipped keyring file is empty or does not parse, and if `checksums.txt.sig` does not verify against it.

Key naming for rotation: create a new key name per rotation (`signing-v2`) rather than a new Transit version, because a new version changes the public key and the Account JWT must list it.

## 5. Bootstrap sequence (once per environment)

1. Deploy OpenBao HA (Raft, 3 nodes) with the seal stanza: HSM/KMS in production, static key from a Secret in test.
2. Operators run `init` with `-recovery-shares=3 -recovery-threshold=2` and PGP-encrypted output, one key per operator. Output is not stored in the cluster.
3. Bootstrap Job (one-time, run with the initial root token, then the token is revoked):
   - enable Transit, KV v2, PKI, Kubernetes auth, an audit device;
   - create Transit keys: operator, operator-signing, sys-account, gateway;
   - build the operator JWT (names operator-signing key and SYS account), sign it with the operator identity key via Transit, sign the SYS Account JWT with operator-signing;
   - write the operator JWT, SYS account public key and operator public key to a ConfigMap (public data);
   - write policies (section 6);
   - revoke the root token and the bootstrap token. Remove the operator identity key's `sign` permission from every policy except bootstrap.
4. Bus nodes start from the ConfigMap (operator JWT, SYS public key). They need no private key.
5. Farmer starts, authenticates to OpenBao with Kubernetes auth, creates the SYS user JWT (signed via Transit), and pushes Account JWTs to every bus node.
6. The job is idempotent: every step checks before it creates.

## 7. Per-tenant provisioning (changed steps)

1. Farmer takes a per-tenant row lease in PXC (the `outbox_lease.go` pattern: a conditional UPDATE on a token and expiry). Not `GET_LOCK`: on PXC it is local to the node that took it.
2. Creates Transit keys for the tenant, reads the public keys, builds the Account JWT (signing key list, limits), signs it with operator-signing.
3. Stores the Account JWT in PXC or object storage, pushes to every bus node, confirms each node has it.
4. Creates the tenant box keypair in KV (existing path).
5. Offboarding: revoke, delete the tenant keys, delete the sprout JWT prefix.

## 8. Per-sprout enrolment (changed steps)

Sprout generates its keys locally. Farmer verifies the join token, asks the tenant signing key (Transit) for the User JWT and the gateway key for the gateway JWT, writes the User JWT to the private object-store bucket, records the sprout in PXC, and returns both JWTs. No per-sprout push to the bus (the sprout presents its own JWT).
Lifetimes (checked in `internal/pki`): the NATS User JWT is minted with no expiry (no `Expires` is set; the tenant Account JWT also has none), so it lives until revoked through the Account's revocation list. The gateway JWT is short-lived (`gatewayjwtttl`, default 24 h) and the sprout refreshes it through the sealed `POST /v1/refresh`; refresh never redeems a join token. Rotating User JWTs is not needed for revocation to work, and adding expiry would require a refresh path for the NATS JWT that does not exist. Decision D5: keep User JWTs until revoked.
Object store rules: separate private bucket, farmer-only credentials, SSE, never served by `/files/`; PXC row lease for mint-or-reuse (D13), so the store needs no conditional PUT; no bucket listing, iterate PXC rows.

### 9.1 Stateless bus: the account loader (D11)

What the NATS server needs: the operator JWT and the system account public key (both public), and its resolver. It never needs an operator or account private key. Account JWTs live in the `full` resolver's `dir` (one file per account), or are baked into the config (`MEMORY` with `resolver_preload`), or are fetched from a URL (deprecated). Nodes of a cluster reconcile with a randomly chosen peer every `interval`. Files placed in `dir` without a push are not enforced.

Flow:

1. Farmer writes `accounts/<account public key>.jwt` and bumps `accounts/index` (a version counter) in the private accounts bucket. Farmer holds the write credential. Each bus node's loader holds a read-only credential for that prefix, and the node's system-account user credential (already a Secret).
2. Bus pod start: the server starts with an empty `emptyDir` and only the operator JWT, system account JWT and `resolver_preload` for the system account. The loader reads every account JWT from the bucket and pushes each one to its own node (`$SYS.REQ.CLAIMS.UPDATE` on localhost). Readiness is false until the loaded count matches the bucket.
3. New tenant, change or revocation: farmer writes the object and bumps the index, then broadcasts an event. The loader pushes the new JWT to its own node. A revocation takes effect on that node as soon as the server applies the update (check what happens to a connected client: test).
4. Missed event: every `N` seconds the loader reads the index object and loads what changed.
5. Replay: the loader keeps the JWT with the latest `iat` per account and refuses to push an older one. Write access to the bucket is farmer-only.
6. Farmer's own push to the nodes (`PushAllAccounts`) stays only as a speed-up and for the SYS account; it no longer decides which nodes hold which accounts, and nothing waits on it.

Tests (our code): a node started empty becomes ready only after loading everything; a missed event is repaired by the timer; an older JWT is not applied; a revoked sprout is refused on every node; all nodes killed and restarted with farmer down.

## 10. Operational implications

- Seal outage plus a pod restart means OpenBao is down: enrolments, tenant provisioning and rotations stop. Already enrolled sprouts keep connecting (the bus holds Account JWTs; sprouts present their own JWTs).
- Recovery needs all three: Raft snapshots, the seal key (with version history), and a recovery-key quorum. Losing any one makes non-exportable keys unrecoverable. Restore must be tested.
- As far as understood, OpenBao standbys forward to the active node, so all Transit signing runs on one node. Use batch signing and load-test enrolment peaks (CONFIRM).
- The operator identity key being in Transit means anyone permitted to sign with it can re-delegate the platform; the permission exists only in the bootstrap policy and is removed after use.
