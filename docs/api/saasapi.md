# SaaS API reference

The SaaS API (`cmd/saasapi`, package `internal/saasapi`) is the service
CloudXP's BFF calls to manage tenants and their fleets. This page describes
what is merged on `main`. The design it implements is
[`cloudxp-machine-manager-api-design.md`](../design/cloudxp-machine-manager-api-design.md);
where the two differ, the code wins, and this page follows the code.

- **Machine-readable spec:** [`saasapi-openapi.yaml`](saasapi-openapi.yaml)
  (OpenAPI 3.1). It was written from the handlers and checked two ways: it
  passes `openapi-spec-validator`, and its paths, methods and
  `operationId`s match `NewRouter` in
  [`internal/saasapi/router.go`](../../internal/saasapi/router.go) one for
  one. Update both together.
- **Where it sits:** see [`docs/diagrams/imas-architecture.svg`](../diagrams/imas-architecture.svg).
  saasapi runs in the non-DMZ core next to farmer, owns the `saas` schema in
  PXC, reads `farmer.*`, and reaches farmer only over the NATS bus.

## Every route is under `/v1`

`NewRouter` registers 16 routes unconditionally, plus 2 behind a feature flag
that is off by default:

|---|---|---|---|
| POST | `/v1/tenants` | `CreateTenant` | 202, async |
| GET | `/v1/tenants/{tenant_id}` | `GetTenant` | |
| PATCH | `/v1/tenants/{tenant_id}` | `PatchTenant` | `name`, `plan_id` only |
| DELETE | `/v1/tenants/{tenant_id}` | `DeleteTenant` | 202, async offboarding |
| GET | `/v1/tenants/{tenant_id}/status` | `GetTenantStatus` | |
| POST | `/v1/tenants/{tenant_id}/enrollment-keys` | `CreateEnrollmentKey` | rate-limited; returns the secret once |

There is no bare `/tenants` route, and the batch GETs take a `{batch_id}`:
there is no route that lists a tenant's batches.

## Authentication

Every route goes through `Auth` (`internal/saasapi/middleware.go`), which
checks two credentials in order. Both are required.

1. **`X-Internal-Auth`**: the BFF's shared secret, compared in constant time
   with `INTERNAL_AUTH_SECRET_CURRENT` and, if set,
   `INTERNAL_AUTH_SECRET_PREVIOUS` (so a secret rotation doesn't cause 401s
   while pods roll).
2. **`Authorization: Bearer <jwt>`**: the end user's Keycloak token,
   forwarded by the BFF. Signature, issuer, audience and expiry are checked
   against `SAASAPI_KEYCLOAK_JWKS_URL`, `SAASAPI_JWT_ISSUER` and
   `SAASAPI_JWT_AUDIENCE`.

On any route with `{tenant_id}`, the token's `organization.id` claim must
equal the path's `{tenant_id}`. A mismatch, or a token without the claim, is
`403 forbidden`. Every failure of either credential is the same
`401 unauthorized`; the reason is logged, never returned.

Two routes have no `{tenant_id}` and so skip the organization check:
`GET /v1/versions` (the catalog is the same for everyone) and
`POST /v1/tenants`. Any caller holding the shared secret and a valid Keycloak
token can create a tenant. The new tenant's id is generated by saasapi
(`t_` + 16 base32 characters), and every later call for it needs a token
whose `organization.id` is that id, so the BFF or Keycloak has to map the
customer's organization to the returned `tenant_id`.

## Errors

Errors saasapi writes itself have one shape:

```json
{ "error": "tenant_not_found", "message": "no such tenant" }
```

`details` is added only where it helps, for example
`{"max": 100}` on `too_many_asset_ids`. Two responses don't use it, because
they come from Go's `http.ServeMux`: a plain-text 404 for a path no route
matches (including the flag-gated routes when the flag is off), and a 405
for a known path with the wrong method.

Codes used across routes: `invalid_request` (400), `unauthorized` (401),
`forbidden` (403), `tenant_not_found` (404), `rate_limited` (429),
`internal_error` (500). Route-specific codes are listed in the spec.

## Resources

### Tenants

`POST /v1/tenants` takes `{"name": "...", "plan_id": "..."}` (`name`
required) and returns **202** with `{"tenant_id": "t_…", "status": "pending"}`.
Provisioning is asynchronous: saasapi writes the tenant and an outbox row in
one transaction, then publishes `internal.tenant.provision` to farmer over
the bus. Poll `GET .../status` until `active` or `failed`. The status
response carries `last_error` when the last job failed, and `warning` when it
succeeded with one.

`DELETE` works the same way in reverse (`offboarding` → `offboarded`) and is
allowed only for an `active` or `failed` tenant. It returns
`409 provisioning_in_progress` while a tenant is still pending, so that the
provision and deprovision requests can't race on farmer.

Statuses: `pending`, `active`, `failed`, `offboarding`, `offboarded`.

### Enrollment keys

`POST .../enrollment-keys` with `{"expires_in_hours": 1–720, "max_uses": 1–10000}`
returns **200** with:

```json
{
  "key_id": "ek_…",
  "registration_key": "ek_….<secret>",
  "expires_at": "2026-10-04T12:00:00Z",
  "max_uses": 50
}
```

`registration_key` is the join token a sprout presents to farmer's
`POST /v1/enroll` (see [INSTALL.md](../INSTALL.md) for how to hand it to a
sprout). Only the SHA-256 of the secret is stored, and this response is the
only place the secret ever appears. Farmer redeems keys against the same
`saas.enrollment_keys` rows, with an atomic `used_count` increment.

`GET` lists keys newest first with a computed `state`: `active`, `revoked`,
`expired` or `exhausted`. `DELETE .../{key_id}` sets `revoked`. It only stops
new enrollments; sprouts that already enrolled with the key keep their
identity.

Key minting is rate-limited per tenant: 1 request/second sustained, burst 5,
tunable with `SAASAPI_ENROLLMENT_KEY_RATE_LIMIT` and `_BURST`, and shared
across pods through Valkey when `SAASAPI_VALKEY_ADDRS` is set
([`deploy/saasapi/README.md`](../../deploy/saasapi/README.md)).

### Asset links and lookup

CloudXP identifies machines by its own `asset_id`. `POST
.../sprouts/{sprout_id}/asset-link` with `{"asset_id": "..."}` attaches one to
a sprout that already exists in the tenant (any key state). A sprout has at
most one asset_id, and an asset_id is globally unique. Creating a new link is
201; repeating an identical link is 200; any other collision is
`409 asset_link_conflict`.

`GET .../sprouts?asset_ids=a1,a2` resolves up to 100 asset_ids to
`{sprout_id, asset_id, key_state, connected}`. Anything that doesn't resolve
in the caller's tenant lands in `unresolved`, and the response doesn't say
why, so it can't reveal whether another tenant holds that asset_id.
`connected` comes from farmer's Valkey heartbeats and is `false` when
saasapi has no Valkey configured.

### Batch actions

`POST .../sprouts/actions`:

```json
{
  "asset_ids": ["vm-001", "vm-002"],
  "action": { "type": "cmd.run", "params": { "cmd": "systemctl restart nginx", "timeout_seconds": 30 } }
}
```

- `type` is `cmd.run` or `cook`. `self_update` is not accepted here.
- `cmd.run` params: `cmd`, and optionally `args`, `cwd`, `run_as` and
  `timeout_seconds` (0–600, default 60). Nothing runs through a shell:
  without `args`, `cmd` is split on whitespace and shell syntax is rejected.
  There is no `env`.
- `cook` params: `recipe`, and optionally `test`.
- The body is decoded strictly (unknown fields are 400) and capped at 64 KiB.
- The tenant must be `active`; otherwise the response is `409 tenant_not_active`.
- Rate-limited per tenant at 1 request/second, burst 5, per pod.

The response is **202** `{"batch_id": "b_…"}`. Items are dispatched to
farmer's `internal.sprout.action` in the background, and farmer re-checks
that each sprout belongs to the tenant before running anything. Poll
`GET .../sprouts/actions/{batch_id}`: the batch is `in_progress` until every
item reaches `unresolved`, `succeeded`, `failed` or
`unresponsive_after_update`. Failed items carry a fixed `error` code and
message (`sprout_not_accepted`, `sprout_unreachable`, `command_failed` with
`exit_code`, `job_failed`, `dispatch_outcome_unknown`, …), never raw error
text.

Dispatch runs in the process that accepted the POST. If that pod dies, its
still-`queued` items stay queued, because the outbox sweeper hasn't been
built yet ([`imas-internal-api-account.md`](../design/imas-internal-api-account.md)).

### Fleet versions and update policy

`GET /v1/versions` lists CloudXP's own published sprout versions (newest
first: `version`, `checksum_sha256`, `released_at`, `notes`). Rows are
written only by `cmd/fleetreleaser`, which signs each one with the
`imas-fleet-signing` Transit key ([`deploy/fleetreleaser/README.md`](../../deploy/fleetreleaser/README.md)).

`GET`/`PATCH .../update-policy` read and set the tenant's
`approved_version`, `auto_update` and rollout window. `null` clears a field.
The version must be in the catalog (`unknown_version` otherwise),
`auto_update` requires an approved version, and the window needs both bounds
with end after start. A tenant with no policy gets the default (nothing
approved, `auto_update: false`), not a 404.

Storing a policy dispatches nothing. With dispatch off, which is the default,
`auto_update` has no effect.

### Fleet update dispatch: not generally available

> **Off by default. Do not enable it in a deployment yet.**
> `POST /v1/tenants/{tenant_id}/sprouts/updates` and
> `GET /v1/tenants/{tenant_id}/sprouts/updates/{batch_id}` are registered
> only when saasapi starts with `SAASAPI_FLEET_UPDATE_DISPATCH_ENABLED=true`
> (`newRouter` in `cmd/saasapi` calls `SetFleetUpdateDispatchEnabled` before
> `NewRouter`). With the default, neither route exists and both paths return
> the ServeMux's plain-text 404.
>
> The reason is that sprout's self-update path is still disabled upstream.
> A sprout verifies and stages a signed release, then the `selfupdate` step
> ends `failed`, because installing it needs the backup/restore work in
> design doc §2.3. `router.go` and `fleet_update_dispatch.go` cite this as
> `yogzblr/imas#286`. That number is from before the repo was renamed and
> doesn't resolve on `yogzblr/imas`.

It is documented here, and in the spec under the `fleet-update-dispatch` tag,
so the contract is on record for when it's enabled. With the flag on:

- The body is `{asset_ids, target_version, batch_size?, gate?}`. `batch_size`
  is 1–25 and defaults to 5. `gate` is `job_status` (the default) or
  `dispatch`. `probe` is rejected, because the probe health signal it needs
  doesn't exist yet.
- `target_version` must be in the catalog, pass the https/checksum/Ed25519
  signature check, be the tenant's `approved_version`
  (`409 version_not_approved`), and now must be inside the rollout window
  (`409 outside_rollout_window`).
- Items go out in waves, and approval and the window are re-checked before
  every wave. One failed wave halts the rest (`rollout_halted`). A sprout
  that doesn't report back within 30 minutes becomes
  `unresponsive_after_update`.
- saasapi also needs `IMAS_FLEETSIGN_OPENBAO_*` (read-only fleet key) with the
  flag on, or it refuses to start.
- Rate limit: one request per 10 seconds, burst 2, per pod.

## Configuration

All from environment variables, read once at startup
(`internal/saasapi/config.go`). A value that is set but invalid is a startup
error, never a silent default.

| Variable | Default | Purpose |
|---|---|---|
| `SAASAPI_LISTEN_ADDR` | `:8081` | HTTP bind address (plain HTTP; terminate TLS in front) |
| `SAASAPI_DSN` | — | MySQL DSN for the `saas` schema |
| `INTERNAL_AUTH_SECRET_CURRENT` / `_PREVIOUS` | — / empty | BFF shared secret(s); `_CURRENT` is required |
| `SAASAPI_KEYCLOAK_JWKS_URL`, `SAASAPI_JWT_ISSUER`, `SAASAPI_JWT_AUDIENCE` | — | Keycloak realm for user JWTs |
| `SAASAPI_NATS_URL`, `SAASAPI_NATS_CA_FILE` | — | farmerbus TLS URL (`:5406`) and the CA that signed it |
| `SAASAPI_NATS_NKEY_SEED_FILE`, `SAASAPI_NATS_USER_JWT` | — | saasapi's SYS-Account NATS User; the seed only as a file path |
| `SAASAPI_VALKEY_ADDRS` | empty | Valkey farmer writes heartbeats to; also shares the key rate limit across pods |
| `SAASAPI_ENROLLMENT_KEY_RATE_LIMIT` / `_BURST` | `1` / `5` | per-tenant limit on minting keys |
| `SAASAPI_FLEET_UPDATE_DISPATCH_ENABLED` | `false` | registers the dispatch routes; leave it off |

saasapi exits at startup if it can't connect to the bus or, when configured,
to Valkey. The Helm chart in [`deploy/helm/farmer`](../../deploy/helm/farmer/README.md)
wires all of this, including delivering saasapi's NATS credential from
OpenBao.
